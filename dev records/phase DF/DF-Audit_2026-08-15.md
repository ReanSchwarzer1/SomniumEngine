## 1. Headline

**`expand_and_wrap` turned every clipmap recentre into a full 1 048 576-texel
ring refresh.** Not an edge case — the common path, on every ring, every time
the camera moved past `UPDATE_MULTIPLE`.

```rust
// crates/somnium_renderer/src/terrain/clipmap.rs, before
if w >= size || h >= size {
    return vec![ClipRect { x: 0, y: 0, w: size as u32, h: size as u32 }];
}
```

`toroidal_dirty_rects` returns the strips that just entered the toroidal
window. The X arm is always **full height** (`wrap_span(x, 0, w, size, size)`);
the Y arm is always **full width**. Adding `EXTENDED_MARGIN` to a full-span
axis pushes it to `size + 4`, which trips `h >= size`, which returns the whole
ring. So the guard fired on every slide, in both arms, forever.

### Why that is the whole phase

`MAX_GEN_TEXELS` is `1024 * 1024` — exactly one ring. The chain:

1. Ring 0 is 512 texels/m, so `UPDATE_MULTIPLE = 16` texels is **3.1 cm** of
   camera movement. Walking retriggers it several times a second.
2. Each retrigger asked for a full 1M-texel regenerate.
3. That is the entire frame budget, so `take_jobs` served **one ring per
   frame** and the other eleven got nothing.
4. `update_ring` returns early while `dirty_count > 0`, so a starved ring stops
   recentring — its centre falls behind the camera.
5. `clipmap_covers` then fails for that ring, and `clipmap_pick_detail_ring`
   skips rings whose `ready` bit is clear anyway.
6. Shading falls through to a coarse ring, the macro stack, or the
   unique-colour fallback.

That last step is what DF-A measured. **The +35.6% walk luminance is this bug,
not evidence that the cache is lossy.** The walk capture was reading a coarse
ring — or `macro_map` — where it should have been reading an 8 m ring at
64 texels/m. `phase_DF.md` §12.3 lists "walk luminance ≤ 1%" as the blocker on
DF-E default-on; the gate was never testing what it thought it was testing.

**Fix:** apply the `>= size` test per axis. An axis that already spans the ring
needs no margin — it wraps onto itself, and the neighbour a bilinear tap wants
is already being written. Three regression tests pin it
(`expanding_a_column_strip_does_not_dirty_the_whole_ring`,
`expanding_a_row_strip_does_not_dirty_the_whole_ring`,
`a_diagonal_slide_stays_cheap_and_fits_the_dirty_slots`).

Order of magnitude after the fix: a 16-texel slide on ring 0 dirties
`(16 + 4) × 1024 ≈ 20k` texels instead of 1 048 576 — about **2% of one frame's
budget** instead of 100% of it. Coarser rings move fewer texels per metre, so
they retrigger proportionally less often. The stack should now stay `ready`
while the camera moves, which is the precondition for everything DF-C designed.

| 7 | `terrain_material.wgsl` | `terrain_strongest_four` = 4×32 iterations over a dynamically indexed `array<bool, 32>`, `array<f32, 32>` passed **by value**, plus a second 32-entry `gated` array and a 32-iteration renormalize whose result is read at four indices | High | Fixed (single pass, 4 scalars) |

### 2.1 Checked and found correct — do not re-audit

- **Generate/shade UV agreement.** Generate maps
  `physical → logical = fract(physical − origin_uv) → world`; shade inverts it
  exactly. Both use framebuffer/texel coordinates with a top-left origin, so
  there is **no Y flip**. Verified algebraically, not by eye.
- **Toroidal invariance under a slide.** With `center' = center + d` and
  `origin' = origin + d·tpm`, `uv` is unchanged for every texel except the
  entered strip: `d/extent = d·tpm/size` cancels. Keeping `ready` set through
  an incremental slide is therefore correct, not a stale-data bug.
- **Ready-bit vs `fill_gpu` ordering.** `take_jobs` flips `ready` before the
  second `fill_gpu`, and generate is recorded into the encoder before shading.
  `queue.write_buffer` lands before the command buffer executes, so the ready
  bits shading sees are the post-`take_jobs` ones. Correct as written.
- **Group 2 array views vs layer `RENDER_ATTACHMENT` views.** Two view sets
  over the same textures, which is the pattern §11 landed on after the compute
  storage path wrote black. Left alone; the storage/copy dead end was **not**
  reintroduced.
- **`set_viewport` + `set_scissor_rect` with a fullscreen-triangle VS.** The
  viewport remaps NDC onto the dirty rect, so only those texels rasterize. The
  in-shader `rect_min`/`rect_max` test is redundant but harmless.

## 3. What each fix changes, and what it risks

### 3.1 Generate cost (findings 1, 2, 3)

Pure win, no visual change: the same texels are generated from the same inputs,
just far fewer of them and in fewer render passes. Covered by unit tests.

### 3.2 Shading occupancy (finding 4)

`ShadingSpec` gains `live_terrain`. When **every** queued terrain is
clipmapped — matching `TerrainClipmap::fill_gpu`'s exact
`enabled && !env_forced_off()` condition — `enable_live_terrain` goes false,
the live branch in `shading.wgsl` becomes statically dead, and
`evaluate_terrain_material` (8 splat fetches, the 32-entry scan arrays, hex,
the POM march and its self-shadow) drops out of the module. Occupancy is the
union of what is *in* the shader, which is the lesson
[`terrain_shading_occupancy_2026-08-14.md`](../terrain_shading_occupancy_2026-08-14.md)
paid for; the clipmap was still paying it.

The condition must keep matching `fill_gpu`. If it ever says "clipmapped" where
`fill_gpu` writes `clipmap_enabled = 0`, the live path is deleted from under a
terrain that still needs it and the ground renders unshaded. That is why the
env-forced-off check is in the loop and why an empty terrain queue keeps the
live path.

### 3.3 Cache precision (finding 5)

The cache now stores `sqrt(albedo)` and the taps square it back. Storage
encoding only — the blend math either side is untouched, and the live path is
not affected at all.

Quantising *linear* albedo to 8 bits is the mistake sRGB exists to prevent, and
because quantisation of a convex curve does not average out it is a systematic
brightness offset, not just banding. **This is the second candidate for the
DF-A luminance miss** after finding 1, and unlike finding 1 it would have
persisted no matter how well the rings tracked.

The macro-map fallback in `evaluate_clipmap_material` was also reading a
perceptually authored map as linear; it is squared now, matching what
`terrain_macro_blend` does on the live path.

### 3.4 Cache sampling (finding 6) — the one to eyeball

`clipmap_load4`'s manual four-tap bilinear is replaced by
`textureSampleLevel` against a **new** sampler at group 2 binding 4: Linear,
Repeat, `anisotropy_clamp: 1`.

§11 records that hardware sampling was tried and "smeared the wrap into streak
bands". The cause was the sampler, not the wrap: the previous attempt used
`default_sampler`, which runs at `anisotropy_clamp: 16` for terrain's grazing
angles. An anisotropic tap takes a *footprint*, and a footprint straddling the
toroidal seam reads texels belonging to the far side of the world. With no
footprint and an explicit LOD, `textureSampleLevel` computes exactly the 2×2
bilinear the manual version computed by hand.

I believe this is provably identical. I have not seen it on a screen. **If
ring-edge streaking reappears in Dbg 32, this is the change to revert** — it is
self-contained in `clipmap_sample` plus the sampler.

### 3.5 Live-path hot loops (finding 7)

This one helps **Coastal with the clipmap off**, i.e. the shipping default, and
is independent of everything above.

Per terrain pixel the old path built `array<f32, 32>` (weights),
`array<bool, 32>` (used), and `array<f32, 32>` (gated), passed the first by
value into `terrain_strongest_four` (a 128-byte copy), ran 4×32 iterations of a
selection sort, then wrote all 32 slots of `gated` and read four of them back.
Dynamically indexed arrays of that size do not stay in registers; that is
scratch-memory traffic on every one of ~2.6M terrain pixels at maximized
Native.

Now: one 32-iteration pass with the running top four in scalars, and four
scalar weights instead of the `gated` array. Output is identical, including the
lower-index-wins tie break (comparisons stay strict, so an equal weight at a
higher index never displaces the one already held). `rt_hit.wgsl` was a third
caller and was updated too — the shader validation test caught it, which is
exactly what that test is for.

## 7. Second round — after the user ran the build (same day)

The user reported real frame-time gains, and one visual problem: **shadows
looking wrong with Clipmap on**, seen as a large dark wedge with straight edges
across a near dune.

### 7.1 That artifact is a regression from finding 1, not a shadow bug

Before the `expand_and_wrap` fix, every slide promoted itself to `mark_full`,
and `mark_full` clears `ready`. Shading skips a ring that is not ready, so the
window between "this ring moved" and "this ring has been regenerated" was never
sampled. Fixing finding 1 made a slide the thin strip it always should have
been — and thin strips leave `ready` **set**, because the rest of the ring is
still valid at the right world positions (the toroidal mapping is invariant
under a matched centre/origin shift; §2.1).

So a ready ring could now serve the strip that had just entered but had not yet
been generated. wgpu zero-fills a new texture, and the shade path took
`occlusion` straight from the cache's alpha, so those texels arrived as
`occlusion = 0`. That zeroes both terms of `evaluate_ibl` — the surface keeps
its direct sun and loses **all** indirect light, which is exactly what a
too-dark, hard-edged region on otherwise correctly-lit ground looks like. It
reads as a shadow problem and is not one.

Two fixes, deliberately belt and braces:

- **`take_jobs` now serves ready rings first.** A ready ring is being sampled
  *this frame*; a non-ready ring is skipped by the picker and its refresh can
  wait. If a ready ring's strip still does not fit the budget, its `ready` bit
  is cleared so the picker falls through to the next coarser ring — a frame of
  lost resolution instead of a hole.
- **Shading rejects an all-zero cache texel.** Generate always writes occlusion
  into alpha and a real blend of layer AO maps is never exactly 0, so `a == 0`
  means "never written". `clipmap_tap_detail` / `clipmap_tap_macro` now return
  invalid for it rather than reporting it as fully-occluded data.

**Not yet confirmed on a screen.** If a dark region survives, **Dbg 8** shows
the occlusion actually reaching the surface and **Dbg 33** shows which ring a
pixel used — those two together separate "cache hole" from "genuine shadow"
in one capture.

### 7.1b Third round — the band with no ripples in it

A second capture showed a different shape: a long dark ribbon lying on the sand,
**flat**, with no ripple detail inside it while the sand around it was fully
detailed. That is not a lighting problem — it is the constant-colour fallback,
and it says two more things were wrong.

- **`clipmap_pick_detail_ring` and `clipmap_tap_detail` disagreed, and nothing
  bridged the gap.** The picker returns the finest ring that is flagged `ready`
  and geometrically covers the pixel. The tap then applies a stricter test and
  can reject. On rejection `evaluate_clipmap_material` dropped **straight past
  every remaining detail ring** to the macro stack, and if that missed too, to
  `vec3(0.35, 0.32, 0.28)` with a flat normal. One ring's worth of missing data
  cost the pixel all eight. The tap now walks outward to the next ring that has
  data; the loop exits on its first iteration in the ordinary case and the
  rings it skips reject on the cheap `ready` / `covers` tests before sampling.
- **The "never generated" sentinel was unsound.** §7.1's guard read alpha `== 0`
  as "no data", but generate writes real blended AO there and an 8-bit AO
  channel can legitimately reach zero in a deep crevice — so a genuinely dark
  texel was being thrown away as missing. Generate now floors occlusion at
  `1/255`, reserving exact zero for the zero-fill. One code is far below what
  the channel resolves.

**Note on §7.1:** the black-wedge diagnosis there was right about the mechanism
(ungenerated texels reaching lighting) but the fix was incomplete, and the guard
it added introduced the false-positive above. Both are corrected here.

### 7.2 More speed with the clipmap **off**

Hex tiling is the biggest multiplier on the live path (three taps per map
instead of one), and it was doing a measurable amount of work twice.

| Change | Was | Now |
|---|---|---|
| Grid + taps per layer | `hex_sample` and `hex_sample_packed_surface` each built their own `hex_grid` and their own three `hex_tap`s from identical arguments | One `hex_taps()` shared by both maps |
| Per-tap rotation | `hex_rot_for` ran `cos` + `sin` per tap, then `hex_rotate` multiplied through — with `HEX_ROT_STRENGTH = 0.0`, i.e. by the identity | `const HEX_ROT_ENABLED` compiles the whole rotation out at the current setting, and restores it if the strength is ever raised |
| `hex_gain3` exponent | `log(1 - r) / log(0.5)` recomputed per weight evaluation, twice per layer | `HEX_GAIN_K` const |

Per layer that is 6 taps → 3, and 4 transcendentals per tap → 2 (the hashed
offset's two `sin` calls, which are the part that actually breaks the lattice).
At four layers: **24 taps' worth of grid/hash/rotation work per pixel down to
6, and 16 `log` calls down to none.** Output is unchanged — the taps never
depended on which map was being read, and the rotation was already the
identity.

### 7.3 Reference check, and what was deliberately not taken

The user asked for reference ideas. What the trees actually say:

- **bgfx `examples/49-hextile`** — the source Somnium's hex path was ported
  from. Its `hextile.cpp` also defaults `m_tileRotationStrength` to `0.0f`,
  which is what makes 7.2's const-fold safe rather than a look change.
- **O3DE `TerrainDetailHelpers.azsli`** — the height-blend and the bounded
  material context are already adopted (25E). Nothing further to take: O3DE's
  remaining trick *is* the clipmap, which is this phase.
- **UE5 `VirtualTextureMaterial.usf` / Landscape** — the camera-independent /
  camera-dependent split is likewise already the clipmap's design (§5.3).

One reference-grounded change was identified and **not** made, because it is a
look risk that wants an A/B rather than an assertion: O3DE runs its *detail*
sampler at anisotropy 16 for terrain's grazing angles, but the splat control
maps and the unique-colour macro map are low-frequency (~2 texels/m) and are
sampled here through the same aniso-16 `default_sampler`. That is 8 anisotropic
fetches per pixel on Coastal for a signal that is immediately renormalised and
collapsed to strongest-four. A dedicated lower-anisotropy sampler for the
control maps is very likely free visually and worth a measurement — but
distant layer boundaries are exactly where it could shimmer, so it should be
captured before it is committed.
